# Course materials map

| Course module | Training-materials deliverable | Planned Target-project progression |
|---|---|---|
| 1. Copilot and project context | Participant guide, prompt cards, FastAPI starter, repository-instructions overlay | Begin with the bare application; add `.github/copilot-instructions.md` during the lab |
| 2A. Skills | Participant lab, trainer notes, prompt card, exact Skill file | Add a reusable API contract review Skill under `.github/skills/` |
| 2B. Hooks | Participant lab, safety discussion, prompt card, Hook configuration and diagnostic script | Add short `preToolUse` and `postToolUse` tool-name diagnostic Hooks only if enabled; otherwise use trainer demo |
| 2C. MCP tools | Participant lab, trainer notes, GitHub Issue brief, prompt card, read-only server config | Add or merge an approved GitHub MCP server in `.vscode/mcp.json`; use OAuth and no committed credentials |
| 3. Testing and feedback | Participant guide, trainer notes, prompts, trainer Issue brief, reusable test-feedback Skill, pytest setup, baseline tests, reference failing validation test, optional `agentStop` test-feedback Hook overlay | Keep the Module 2 diagnostic Hook for tool-name observation; after learners add and understand the red test, optionally add the separate Module 3 Hook for bounded pytest feedback during implementation/verification; run pytest manually if unavailable |
| 4. Requirements | Ambiguous feature request, clarification exercise, acceptance-criteria worksheet, reusable requirements Skill, Miro evidence, session-start Hook | Read request, code/tests, and Miro flow; record approved decisions, assumptions, and open questions |
| 5. Lightweight Spec-Driven Development | Reusable spec-planning Skill, feature specification and task/story templates, scope-change exercise | Convert reviewed requirements into dependency-ordered, testable stories linked to criteria and Miro evidence |
| 6. Incremental implementation | Implementation Skill, test-first story task sequence, session handoff template | Implement the first Jira story in reviewable test/code steps and carry verified status forward |
| 7. Capstone part I | Significant feature menu, Miro/Jira briefs, capstone vertical-slice Skill, branch/task guidance | Choose a feature, refine scope, create the story plan, and build its first vertical slice on a branch |
| 8. Review and safeguards | Review checklist and deliberately imperfect change | Inspect diff, tests, validation, authorization, dependencies, and security requirements |
| 9. Miro-to-Jira story delivery loop | Miro/Jira integration workflow, story prompts, delivery log template, code-exploration and regression-test steps | Read Miro evidence, create reviewed Jira stories, retrieve and implement each story sequentially, then commit and push its branch |
| 10. GitHub Actions CI and runtime verification | GitHub Actions workflow, live HTTP smoke script, optional Dockerfile and Cloud Run staging guide, CI-failure exercise | Run tests and a live service check on pushes/PRs; diagnose a CI failure; optionally deploy through a separately approved staging path |
| 11. Capstone part II: pull request to verified result | Participant guide, PR template, final verification handoff, review/presentation prompts | Finish the remaining approved capstone work; review the final diff and test evidence; open a PR; use Module 10's existing Actions workflow as a required check; resolve review/CI findings; merge only when authorized; verify locally or in the prepared staging environment; present decisions and limitations |
| 12. Practical judgment and wrap-up | Participant guide, capstone assessment checklist, reflection prompts, trainer notes | Assess the complete Miro/Jira-to-verified-change workflow; decide where Copilot helps, where human judgment/review is essential, and which small practices the team will adopt |

Miro is introduced as a product-evidence source in Module 4 (with a board-export fallback), and Jira becomes the story source of truth for implementation in Modules 5–9. Figma is used when a UI-bearing story has a design frame; the current API-only Target does not make Figma relevant to every story. Module 10 owns CI in GitHub Actions; Cloud Run is a separate optional, manually approved staging path, not an automatic push-triggered deployment. Each module folder should contain participant instructions, trainer notes, and any exact Target-project artifacts. Guides must name copied paths and mark them **ADD**, **REPLACE**, or **MERGE**.
